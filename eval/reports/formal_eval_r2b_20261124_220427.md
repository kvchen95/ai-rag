## 5. 阈值标定结论

- `python eval/calibrate.py --report eval/reports/redline_20261124_220427.json --name r2b_20261124_2207`：**退出码 2，结论"不可标定"**。
- 扫描 t=0.20…0.60：应答题 TP=0/FN=35，拒答题 FP=0/TN=13，TPR=FPR=0%，**Youden 恒为 +0.00**，不存在波谷，也不存在任何可由数据支持的候选阈值。
- 0.20/0.40 是否要重标：**否，本轮不动**。原因是输入数据退化（top1 全 null），不是阈值不合适；把 0.20 下调不会改变 `scored=0 → 0.000 → 拒答` 的链路，调到 0 则等于取消门控——两种方向都无证据支撑。
- **缺什么**：（a）精排正常返回后的有效 top1（应答题与拒答题都要有，且 rerank `scored>0`、无 `degrade`）；（b）修好后再跑一轮 `make eval` 得到同语料版本的分数分布；（c）之后再谈 Youden / 波谷候选。当前样本 35/13 即使有分数，命中率 95%CI 半宽约 ±16.6pp / ±27.2pp，只能给"区间候选"，不足以精确验收。

## 6. golden `expected_doc_key` 核查（单列，避免误判引用正确率）

## 7. 限制与风险

1. 本轮只有 1 次评测运行；`rerank_timeout` 是稳定复现还是瞬时抖动，需修复/复跑确认（超时时间为 801–815ms，紧贴 800ms 预算上限，倾向于预算不足而非随机故障）。
2. 诊断探针（只读、未改配置）：api 容器内直连 rerank，8 条短文本 HTTP 200 / 0.65s；8 条约 502 字的真实长度文本 HTTP 200 / **2.24s**——与 800ms 预算明确冲突。该探针不在评测流程内，仅作根因佐证。
3. 7 道应答题零候选（`超出库范围，未检索`）属于时间范围/语料覆盖问题；即便精排修好，这 7 题仍会拒答，需单独处理。
4. 无有效 top1 ⇒ 无法判断精排能否区分应答题与陷阱题；不能推断"降低阈值就能提覆盖率"，也不能推断"当前阈值过严"。
5. 语料在评测前由父任务 promote 至 active=9；本卡未改库、未改阈值、未改 golden；评测后 `ingest-status` 未发现漂移变化。
